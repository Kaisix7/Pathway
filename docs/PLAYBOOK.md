# Регламент аварийного восстановления (Operations Playbook)

Данный документ содержит пошаговые инструкции по устранению критических инцидентов и аварийных ситуаций (Runbooks / Playbook) на продакшн-окружении бэкенда.

---

## Сценарий 1: Сайт или API недоступны (Service Down)

### Симптомы:
* Ошибка `502 Bad Gateway`, `504 Gateway Timeout` или `Connection Refused` при запросах к API.
* Эндпоинт проверки здоровья `/api/health/` не отвечает или возвращает статус `503 Service Unavailable`.
* Внешний мониторинг присылает алерт **"Service Down"**.

### Шаги по устранению:
1. **Проверьте панель управления Render:**
   * Зайдите на [dashboard.render.com](https://dashboard.render.com) и выберите сервис `pathway-backend`.
   * Посмотрите статус веб-службы (должен быть зеленый индикатор `Live`).
2. **Проанализируйте логи веб-службы:**
   * Перейдите во вкладку **Logs** в Render.
   * Найдите ошибки запуска приложения (например, `Traceback`, сбои импортов или ошибки синтаксиса).
3. **Проверьте доступность базы данных:**
   * Проверьте статус базы данных в Render (вкладка базы данных PostgreSQL).
   * Если БД переполнена или зависла, перезапустите её.
4. **Выполните перезапуск сервиса:**
   * В панели управления Render в верхнем правом углу нажмите кнопку **Manual Deploy** ➔ **Clear Cache & Deploy** (или **Restart Service**).
5. **Если падение вызвано плохим деплоем (Rollback):**
   * Если сбой произошел сразу после слияния ветки в Git, верните предыдущий коммит:
     ```bash
     git checkout main
     git revert HEAD
     git push origin main
     ```
   * Render автоматически соберет и запустит стабильную предыдущую версию.

## Сценарий 2: Оплата подписок не проходит (Payment Fails)

### Симптомы:
* Пользователи жалуются, что после успешного списания денег на стороне Stripe тариф не меняется на Premium.
* Приложение показывает ошибку `Error verifying payment: ...`.
* В логах бэкенда появляются записи уровня `ERROR` с тегом `payment_error` или сообщениями `Error verifying Stripe session`.

### Шаги по устранению:
1. **Проверьте статус Stripe API:**
   * Зайдите на [status.stripe.com](https://status.stripe.com) и убедитесь, что шлюз Stripe не испытывает глобальных проблем.
2. **Проверьте ключи аутентификации:**
   * Перейдите во вкладку **Settings** ➔ **Environment** на Render.
   * Убедитесь, что переменная `STRIPE_SECRET_KEY` установлена и не просрочена.
3. **Проверьте логи ошибок транзакций:**
   * Отфильтруйте логи на Render по ключевому слову `payment`.
   * Найдите конкретный `session_id`, по которому произошел сбой, и изучите детали ошибки (например, `No such checkout.session`).
4. **Ручное исправление статуса пользователя (при необходимости):**
   * Если оплата прошла на стороне Stripe, но бэкенд не активировал Premium из-за сетевого сбоя:
     1. Зайдите в Django Admin (`https://pathway-backend-htas.onrender.com/admin/`).
     2. Перейдите в раздел **App users**.
     3. Найдите пользователя по email и вручную переключите поле **Plan** с `free` на `premium`.

## Сценарий 3: Высокий уровень ошибок (High Error Rate >5%)

### Симптомы:
* Внешний мониторинг отправляет алерт **"Error Rate >5%"**.
* Запросы к API возвращают коды ответов `500 Internal Server Error`.
* Метрики на Render показывают резкий спад доли успешных ответов (HTTP 2xx/3xx) и рост HTTP 5xx.

### Шаги по устранению:
1. **Сбор информации из JSON-логов:**
   * Скачайте или отфильтруйте логи в панели Render.
   * Поскольку логи пишутся в формате JSON, найдите строки с уровнем `'level': 'ERROR'`.
   * Определите источник ошибки (какой эндпоинт возвращает 500, например `/api/login/` или `/api/register/`).
2. **Проверка утечки соединений или блокировок БД:**
   * Выполните проверку здоровья базы данных через эндпоинт `/api/health/`.
   * Проверьте загрузку CPU и RAM на Render. Если RAM превышает 100% лимита тарифа Free (512 МБ), сервис начинает уходить в OOM (Out Of Memory) и перезапускаться по кругу.
3. **Очистка кэша Redis:**
   * Если сбои вызваны некорректными данными в кэше или зависшими сессиями 2FA, сбросьте кэш Redis.
   * Подключитесь к бэкенду локально или через консоль Render Shell и выполните команду сброса:
     ```python
     python backend/manage.py shell -c "from django.core.cache import cache; cache.clear()"
     ```
4. **Масштабирование/Оптимизация:**
   * Если высокий Error Rate вызван наплывом пользователей (нагрузка), временно увеличьте количество инстансов (Scale Up) в настройках Render до платного тарифа с автоскейлингом.
